# 03 - Google SSO with Helix Authentication

## Parts
| Part | Role |
|---|---|
| **Helix Authentication Service** (Node.js) | Talks OIDC to Google; hands the verified profile to Helix Core |
| **Helix Authentication Extension** (in `p4d`) | Intercepts `p4 login`, sends the user to the service, compares identities, issues the ticket |
| **Google OAuth client** | Identifies our service to Google |

## Google Cloud Console (one time)
1. APIs & Services -> Credentials -> **Create OAuth client ID -> Web application**.
2. **Authorized redirect URI:** `<service base URL>/oidc/callback`. Reference setup: `https://localhost:3000/oidc/callback`. Live: your real service address.
3. Save the **client ID** and **client secret** into the secrets folder yourself. Never paste them in chat, tickets, or the depot.
4. Consent screen:
   - **Internal** (Google Workspace): only your organisation's accounts can sign in. **Use this for live.**
   - **External + Testing** (testing with a personal `@gmail.com`): you must list every user under **Audience -> Test users**, or Google shows "Access blocked".

## Service configuration (generated by `03-configure-auth-service.ps1`)
| Setting | Value | Why |
|---|---|---|
| `OIDC_ISSUER_URI` | `https://accounts.google.com` | Google discovery endpoint |
| `OIDC_CLIENT_ID` / `OIDC_CLIENT_SECRET_FILE` | from your Google client | Secret is read from a locked file, not the config |
| `OIDC_CODE_CHALLENGE_METHOD` | `S256` | PKCE |
| `OIDC_SELECT_ACCOUNT` | `true` | Google account chooser, so users pick the right account |
| `SVC_BASE_URI`, `CERT_FILE`, `KEY_FILE` | HTTPS URL and certificate | Browsers and the extension connect over TLS |
| `CA_CERT_FILE` | CA that signs the extension's client certificate | Only the Helix extension may fetch user profiles |
| `SESSION_SECRET`, `BEARER_TOKEN_FILE` | random | Generated per install |

Health check: `https://localhost:3000/status` should show `"oidc":{"oidc":"ok"}`.

## How identity matching works
The extension asks the service for the user behind the login, then compares:
- the **email claim** from Google (`name-identifier: email`), and
- the **Email** field of the Perforce user (`user-identifier: email`).

They must be identical. Consequences:
- Creating a Perforce user with the wrong email means that person cannot log in (safe failure).
- Signing in with the wrong Google account is refused. Real example: running `p4 login` as `arizlan` (email `arizlan@mitrai.com`) but signing in with `ahamedrizlan2002@gmail.com` gave `Login invalid` and the extension log said `identifiers do not match`.
- Because users are created only by admins, a valid Google account alone does not grant access.

## Where to look when it fails
| Log | Location (reference setup) |
|---|---|
| Extension | `D:\helix\server\root\server.extensions.dir\<uuid>\1-data\log.json` |
| Authentication Service | `D:\helix\logs\has.out.log`, `has.err.log` |
| Helix Core | `D:\helix\server\root\p4d.log` |

Useful log lines in the extension log: `received user data` (what Google sent), `comparing user identifiers`, `identifiers do not match` or `identifiers match`.

## Non-SSO accounts
`p4admin` (break-glass) and `svc-auth` are listed in `non-sso-users`. Everyone else must use SSO.
